# AI PLM Secure Object Storage Policy

## 1. 목적

본 정책은 AI PLM에 신규로 저장되는 모든 공식 파일의 저장·보안·복원 원칙을 정의한다.

대상은 사용자 업로드 문서, 도면, 품질 첨부, 이슈·리스크 첨부, 워크플로우 첨부, 보고서, AI 생성 공식 문서 등 PLM에서 물리 파일로 관리되는 모든 자료를 포함한다.

기존에 이미 저장된 파일은 즉시 재배치하거나 재암호화하지 않고 현행 구조를 유지하며, 본 정책 적용 이후 신규 등록 파일부터 적용한다.

## 2. 기본 원칙

1. 물리 저장소의 폴더 구조는 업무 의미를 갖지 않는다.
2. 프로젝트, WBS, 문서/도면 구분, Revision, 출처, 승인 상태 등 모든 논리 관계는 PostgreSQL에서 관리한다.
3. 애플리케이션은 실제 물리 경로를 직접 사용하지 않고 Storage Adapter와 object key를 통해서만 파일을 접근한다.
4. 물리 저장 파일에는 원본 파일명, 확장자, 프로젝트명, 고객명, 도면번호, Revision 등 식별 가능한 업무 정보를 노출하지 않는다.
5. 신규 공식 파일은 시스템이 발급한 무의미한 object key로 저장한다.
6. 물리 저장소만 복사해서는 원본 파일을 식별하거나 정상적으로 열 수 없도록 한다.
7. 열람·다운로드·미리보기는 AI PLM 권한 검증을 거친 API를 통해서만 수행한다.

## 3. Secure Object Storage

물리 저장 파일은 UUID 또는 동등 수준의 비식별 object key를 사용한다.

예시:

```text
objects/
  9f/
    9f7a21c4e9b8429ba1d6f301a44e8f27.obj
```

위 파일명만으로는 원본 파일 종류, 프로젝트, 도면번호, 문서명 또는 Revision을 유추할 수 없어야 한다.

폴더 분할 방식은 저장 효율과 운영 편의를 위한 내부 구현으로만 사용하며 제품의 업무 로직과 결합하지 않는다.

## 4. 암호화 정책

신규 공식 파일은 기본적으로 파일 내용을 암호화하여 저장한다.

- 권장 알고리즘: AES-256-GCM 또는 동등 수준의 인증 암호화 방식
- 파일별 랜덤 nonce/IV 사용
- 암호화 키는 파일 저장소 및 업무 DB와 분리하여 보관
- DB에는 실제 키 자체가 아닌 key identifier 등 필요한 최소 메타정보만 저장
- 복호화는 권한이 확인된 AI PLM 애플리케이션을 통해서만 수행

목표는 다음과 같다.

> 저장소 파일과 DB 백업만 확보한 상태로는 원본 파일을 정상 복원할 수 없어야 한다.

## 5. DB 메타데이터

PostgreSQL은 파일의 업무 의미와 복원에 필요한 메타데이터를 관리한다.

예시 항목:

- deliverable/document/drawing 식별자
- version/revision 식별자
- original_file_name
- content_type
- file_size
- storage_object_key
- encryption_key_id
- nonce/IV 및 인증에 필요한 메타정보
- checksum
- source(uploaded / ai_generated / linked 등)
- 생성자 및 생성 시각

물리 저장소에는 위 업무 정보를 중복하여 파일명이나 폴더명으로 표현하지 않는다.

## 6. AI 생성 문서

AI 대화 중 임시 텍스트나 아직 공식 저장되지 않은 초안은 Secure Object Storage 대상이 아니다.

AI 결과가 DOCX, PDF, XLSX, PPTX 등 실제 파일로 생성되어 사용자가 저장하거나 공식 산출물로 등록하는 순간부터 일반 사용자 업로드 파일과 동일한 저장 정책을 적용한다.

즉 파일의 생성 주체와 관계없이 PLM에서 공식 파일이 되는 시점부터 동일한 Secure Object Storage를 사용한다.

## 7. Storage Adapter 원칙

모든 신규 파일 저장·읽기·삭제는 단일 Storage Adapter를 통해 수행한다.

애플리케이션 코드에서 로컬 디스크, NAS, S3/MinIO 등의 실제 경로 또는 SDK를 직접 호출하지 않는다.

지원 대상은 구현 확장에 따라 다음과 같이 구성할 수 있다.

- Local/File Server
- NAS
- S3-compatible Storage / MinIO
- AWS S3
- Azure 계열 Object Storage

Storage backend가 변경되어도 상위 애플리케이션 로직과 DB 모델은 변경되지 않는 것을 원칙으로 한다.

## 8. 성능 원칙

보안 적용으로 사용자 체감 성능이 유의미하게 저하되지 않아야 한다.

- 대용량 파일 전체를 메모리에 적재하는 구현을 피한다.
- 가능하면 업로드 시 암호화 스트리밍, 다운로드 시 복호화 스트리밍을 사용한다.
- DWG Preview PDF, 썸네일 등 파생 파일은 최초 생성 후 재사용한다.
- 프로젝트 또는 WBS에 동일 자료를 연결할 때 물리 파일을 반복 복사하지 않고 DB 관계를 생성하는 방식을 우선한다.

## 9. 접근 통제

물리 저장소는 일반 사용자가 직접 접근하는 공유폴더로 제공하지 않는다.

- PLM 서비스 계정에 필요한 최소 권한 부여
- 일반 사용자 직접 파일시스템 접근 차단
- 다운로드/미리보기는 PLM API를 통해 제공
- 주요 열람·다운로드·삭제 작업은 감사 로그에 기록할 수 있도록 설계

## 10. 적용 범위 및 전환 원칙

본 정책은 정책 적용 이후 신규 저장되는 파일부터 적용한다.

기존 파일은 즉시 일괄 변환하지 않고, 별도의 마이그레이션 계획이 승인되기 전까지 기존 저장방식을 유지한다.

신규 기능 개발 시 문서, 도면, 품질, 이슈, 워크플로우, AI 생성 문서 등 기능별 별도 저장방식을 새로 만들지 않는다.

모든 신규 공식 파일은 동일한 Secure Object Storage 정책과 Storage Adapter를 사용한다.
